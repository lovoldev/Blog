> In recent years, for Android developers, the trendiest technology has been Jetpack.webp Google has been actively promoting the use of Jetpack since 2019, and after all this development, Jetpack has basically fulfilled the design goals it set out to achieve at the time — simple, consistent, and focused.webp And the cornerstone that made all of this possible, I think, is the Architecture Components.webp Initially, the Architecture Components had little connection to the support library as a standalone library, but as Jetpack took shape, it also injected new vitality into the Architecture Components.webp In the Jetpack library, Architecture Components are used everywhere and play an increasingly important role.webp Today, I'll start with Lifecycle, the cornerstone of the Architecture Components, and attempt to dissect them, showing you how Google developers design a library with high cohesion and low coupling.webp

## Preface
To talk about reading source code, I think it's the same as putting an elephant in a fridge — no matter how big the task, it has to be broken into steps.webp The first step in reading source code is to stand in the developer's shoes and extract the functionality the library needs to accomplish.webp Only by clarifying the functionality can you design code around it, which is also the second step of reading source code — understanding the implementation logic.webp We can use UML diagrams to help us understand.webp Usually, once the UML diagram is drawn, our understanding of the source code is mostly there.webp At this point, we can move to the third step: savoring the implementation details.webp With the foundation of the first two steps, we can selectively pick topics of interest to study the implementation, and we can do so with ease and precision.webp

Let's get started!

## The source code approach of Lifecycle
Clarify Lifecycle's design goal
In one sentence, Lifecycle accomplishes the task of lifecycle awareness.webp What does lifecycle awareness mean? It means a class can correctly handle state updates without depending on Activity or Fragment callbacks.webp So why do we need such a class? What's the difference between this and writing logic directly in the callback methods? To answer this question, let's imagine a scenario: an Activity needs to obtain the user's real-time location and also needs to use the camera.webp Previously, our approach was to set up location and camera listeners and unlisteners in certain callbacks of the Activity.webp If the Activity then adds other logic, its code can balloon to an unbearable size, and as the business grows, the subsequent bloating of the Activity is unpredictable, which is not conducive to debugging and testing.webp Moreover, from a design perspective, such a design is also fragile and too tightly coupled.webp But these components of ours genuinely do need to respond to lifecycle callbacks.webp So how can we both perceive the lifecycle and reduce coupling? Computer science tells us one truth: when no other method can be found, consider adding a layer of abstraction.webp Thus, Lifecycle was born.webp That is Lifecycle's goal, and it's very pure — it's just lifecycle awareness, leaving professional work to professionals.webp

## The workflow of Lifecycle
In summary, Lifecycle accomplishes two functions: state monitoring and state dispatch.webp To complete these two functions, Lifecycle abstracts three concepts, which can also be thought of as three stages.webp
1.webp The object that owns the lifecycle is called the LifecycleOwner.webp This is really just an interface — anything that can provide a Lifecycle can be called a LifecycleOwner.webp The main function of this class is to provide raw lifecycle events as data for subsequent operations.webp This is the first step — state awareness;
2.webp The object that owns the lifecycle state is called Lifecycle.webp The main function of this class is to provide state abstraction and state information.webp This is the second step — state update;
3.webp The observer interested in the lifecycle state is called LifecycleObserver.webp The main function of this class is to respond to the state information.webp This is the third step — state response.webp

The flow is simple and looks quite clear — it's the observer pattern.webp But to achieve better decoupling and provide more extensibility, the Lifecycle library derived more classes in these three stages, which is also why I chose Lifecycle as the object of analysis.webp I think a good library not only needs to fulfill its design goals, but should also maintain as much extensibility and readability as possible.webp In this respect, Lifecycle is undoubtedly a great role model for us.webp Next, let's take these three stages as the main thread and dissect, one by one, how Lifecycle completes its abstraction, design, and implementation.webp

### Lifecycle's state awareness
Traditional state awareness involves overriding the lifecycle callbacks of Activity and Fragment and updating state within the callbacks.webp This is actually also the basic approach of Lifecycle's implementation; it just abstracts these callbacks into individual events.webp So how do we convert the lifecycle into individual events? Lifecycle uses a clever method by defining a custom ReportFragment.webp ReportFragment's role is very clear: it monitors the lifecycle and generates state events.webp
![ReportFragment interface list](/images/posts/jetpack-lifecycle/reportfragment.webp)
As shown in the figure, in essence ReportFragment still monitors the Activity's lifecycle, and the binding relationship is established in the `injectIfNeededIn` method.webp Then, to pass the monitored state out to other classes for use, ReportFragment relies on the `dispatch` method.webp There's a very clever design detail here: `dispatch` doesn't directly reference its own component, but instead uses the Activity.webp So why can the event still be sent out? Because dynamic type checking and casting are used here, and ultimately it's cast to the dispatcher LifecycleRegistry to complete the event dispatch operation.webp This smoothly moves the logic to the second stage: state update.webp

### Lifecycle's state update
The main logic for state update is placed in the LifecycleRegistry class, which inherits from Lifecycle.webp
![LifecycleRegistry interface list](/images/posts/jetpack-lifecycle/lifecycleregistry.webp)
As shown in the figure, as a subclass of Lifecycle, this class completes the two functions of the observed object: receiving and managing the observers.webp Secondly, as a core class, it completes the state update function.webp Events are converted into states here, saved, and then its observers are notified.webp From the class overview, we can also see that these methods are designed precisely to accomplish these two major functions.webp Once we know this, the steps for state update are understood.webp Then, naturally, we move right into the third step.webp

### Lifecycle's state response
LifecycleObserver is an empty interface, so how is the state update done? We still have to start from LifecycleRegistry.webp LifecycleRegistry wraps the LifecycleObserver when it's added, so the LifecycleObserver becomes various subclasses of LifecycleObserver, and within the different subclasses, they all directly or indirectly inherit from LifecycleEventObserver.webp So ultimately the state is notified to the observer through the `onStateChanged` method of LifecycleEventObserver.webp But we soon notice something's off — the official demo directly implements LifecycleObserver and only needs to register for the states of interest using annotations.webp There's no trace of that here.webp Following our previous approach, we still start from the method that adds the LifecycleObserver.webp The LifecycleObserver is wrapped into an ObserverWithState object, and the constructor delegates to Lifecycling, so the secret ultimately lies in Lifecycling.webp Lifecycling processes multiple kinds of LifecycleObservers, including the annotation-based approach we're familiar with.webp So, to summarize, after we define a LifecycleObserver observer through annotations and register it with LifecycleRegistry, it gets wrapped into a new observer object.webp Then, during state updates, the annotation is used to find the appropriate method to notify the observer.webp At this point, the entire workflow of Lifecycle has been clarified, and I've compiled a UML diagram based on it.webp
![Lifecycle UML diagram](/images/posts/jetpack-lifecycle/lifecycle.webp)
From the UML diagram, we can intuitively reach a one-sentence conclusion: LifecycleRegistry uses the Lifecycle provided by the LifecycleOwner, and uses the observer pattern to pass the state to the LifecycleEventObserver.webp This is the connection between the three abstractions I mentioned at the very beginning.webp

## Savoring the implementation details
After reading through it many times, I've discovered several small details of Lifecycle worth savoring.webp The first is Lifecycle's powerful abstraction.webp Lifecycle uses LifecycleOwner to abstract away the concept of lifecycle; the lifecycle doesn't have to be bound to an Activity — users can define their own LifecycleOwner and customize a Lifecycle that suits their business needs.webp Secondly, LifecycleRegistry is an excellent example of high cohesion and low coupling — LifecycleRegistry only depends on top-level interfaces like LifecycleOwner and LifecycleObserver, following the dependency inversion principle.webp LifecycleRegistry's internal wrapping of the LifecycleObserver is delegated to Lifecycling, following the single responsibility principle.webp Even LifecycleRegistry's methods strictly adhere to the single responsibility principle.webp One can't help but admire the developer's strong command of the code.webp

Of course, there are other nice implementation details that I haven't expanded on one by one, because code can never be fully read — we just grab what we're interested in.webp Some details are meant to be ignored, and we have to admit that fact.webp
