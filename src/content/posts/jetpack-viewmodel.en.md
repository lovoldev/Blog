> As one of the three veterans of the Architecture Components, ViewModel is a powerful weapon for implementing MVVM.

## ViewModel's design goal
ViewModel's basic function is to manage the UI's data. In fact, from a responsibility standpoint, this is yet another functional split of Activity and Fragment. The data previously stored inside them required them to handle the entire process of creation, update, storage, and restoration on their own, while they also had to handle UI data binding, updates, animations, and other operations. A multiplicity of responsibilities makes problems hard to locate and debug. In addition, as the bearers of the UI, Activity and Fragment often need to share data and reuse functionality. And the differences in UIs make it hard to control the granularity of reuse, making it easy to write code with poor extensibility. Based on these pain points, ViewModel was designed.
At the same time, ViewModel also strengthened the data preservation feature — it automated the saving and restoration of data across configuration changes, ensuring data validity throughout the UI's lifecycle. This greatly reduces boilerplate code and improves development efficiency.

## ViewModel's architecture design
***ViewModel uses two levels of granularity to complete the data management functionality.*** The first level is the management of the data stored by ViewModel itself. Its goal is to complete the creation of the ViewModel, and the corresponding abstraction entity is `ViewModelProvider.Factory`. The second level is the management of existing ViewModel groups, whose goal is to ensure the validity of ViewModels under unexpected circumstances; the corresponding abstraction entity is ViewModelStore. Of course, these are all just conceptual abstractions; they still need a glue to embody their levels of abstraction, and that is ViewModelProvider. These three main classes jointly build the framework of the ViewModel system. The remaining classes are supplements and refinements to these three concepts. Next, I'll use these abstractions as the main threads and analyze their implementation logic layer by layer.

## ViewModel's group management
As mentioned earlier, ViewModelStore completes group management, so the first thing we should determine is the concept of a group — that is, who these ViewModels belong to. This isn't hard to understand: to manage a group, you have to find the group's owner. This leads to ViewModelStoreOwner, which represents an object with group management authority. Through the ViewModelStore object it provides, you can manage the ViewModels inside it, and these ViewModels together form a group. So ViewModelStoreOwner is actually the abstraction entity of a group; it represents a group and is also the unit for managing groups.
ViewModel has two groups implemented by default — ComponentActivity and Fragment. That is, both ComponentActivity and Fragment implement the ViewModelStoreOwner interface.
Let's first look at ComponentActivity's implementation. According to the interface, first look at the implementation of the interface method `getViewModelStore`. It mainly involves two objects. One is the ViewModelStore reference `mViewModelStore`; the other is very interesting — it's a NonConfigurationInstances object, which is a simple class used to hold the ViewModelStore object. So what's special about it? It's the return object of the `onRetainNonConfigurationInstance` method.

> A quick extracurricular knowledge share: `onRetainNonConfigurationInstance` is a method of Activity. This method is automatically called by the system when a device configuration changes (such as when switching between portrait and landscape), and is used to let the user save data. As long as this method returns an object, it won't be destroyed when the device configuration changes. Later, after the rebuild is complete, it can be retrieved through the `getLastNonConfigurationInstance` method.

Let's return to the implementation of `getViewModelStore`. Just now I mentioned the NonConfigurationInstances object, which is obtained by calling the `getLastNonConfigurationInstance` method. If the method returns a valid object, it means the Activity has been rebuilt; then it directly retrieves the value saved in the NonConfigurationInstances object and updates `mViewModelStore`. Otherwise, it means there's no valid ViewModelStore object yet, so it creates one directly. From this logic, it's easy to see that our ViewModel won't be rebuilt with device changes, which exactly satisfies our design goal. So what about Fragment? How is its implementation different?
Fragment's implementation is more convoluted. It directly delegates to FragmentManager, which delegates to the `getViewModelStore` method of FragmentManagerViewModel. The method implementation is also very simple — it's just a `HashMap` lookup, creating a new one if it doesn't exist. This is clearly not what we want to see, because there's no logic for handling state changes like Activity has. So the only breakthrough point is that `HashMap` object. After searching around, we find that it's returned as the return value of the `getSnapshot` method, which has a bit of an Activity flavor to it. Tracing back up, we find that ultimately, as a non-destroyed object, it's saved before the Fragment is destroyed.
The above is the creation logic of ViewModelStore in the two application scenarios. In addition, there's also the cleanup logic that hasn't been covered. In essence, this logic calls ViewModelStore's `clear` method, and the only issue is determining when to call it. Specifically, Activity registers a `Lifecycle` state listener and calls the `clear` method at `Lifecycle.Event.ON_DESTROY`, while Fragment continues to use FragmentManager's `desctory` method as the entry point for the call. The method call is completed in FragmentManagerViewModel.
To summarize, ViewModelStoreOwner is an abstraction of a ViewModel group. Although it corresponds to two different implementations, they lead to the same end by different routes: ***the ultimate goal is to ensure the validity of the corresponding ViewModelStore object when the device configuration changes,*** thereby ensuring the validity of the ViewModel objects. At the same time, it does the cleanup work when destruction is truly needed. This is ViewModel's group management functionality.

## ViewModel's creation management
ViewModel uses `ViewModelProvider.Factory` to manage the creation process. Specifically, it's about how to create the corresponding object based on the class information of a ViewModel subclass. There are two difficulties here — the necessary dependency injection and data restoration. For dependency injection, ViewModel plays the same old trick as with creating ViewModelStore: it provides a `HasDefaultViewModelProviderFactory` abstraction and shifts the dependency injection to ComponentActivity and Fragment. The reason for doing this is that creating a ViewModel may require information like Application and Bundle, which can only be obtained in Activity and Fragment. Data restoration focuses on how to use existing data to restore an object to its original state. Of course, all these processes can be omitted — if you don't need to pass Application or Bundle objects and don't need to restore the ViewModel state, the library provides a default implementation, which simply creates the object by reflection.
For all the situations just mentioned, `ViewModelProvider.Factory` has multiple implementations. So which implementation does it actually use? We have to find the answer in ViewModelProvider. In its constructor, it performs type checking on the ViewModelStoreOwner; if it's an instance of `HasDefaultViewModelProviderFactory`, it uses the object returned by the instance; otherwise, it uses the default implementation. Combining this with the analysis above, let's continue to look for the answer in ComponentActivity and Fragment. You'd never guess what we find — they both use the SavedStateViewModelFactory class. So let's take a look at how it's implemented.
When constructing a SavedStateViewModelFactory object, three objects are passed in — Application, SavedStateRegistryOwner, and Bundle. The most important of these three is the second; its main function is to provide the SavedStateRegistry object, which saves data at the appropriate time and then restores it at the appropriate time. It's also a lifecycle-aware component. In its `create` method, the ViewModel object is also constructed via reflection; the only difference is that the reflection has one more parameter. Continuing on, this information is ultimately used to construct a SavedStateHandle object, and this object is what actually holds the useful information for the ViewModel object we're currently creating. SavedStateHandle provides methods for saving data by key-value pairs and query methods as well, so a ViewModel can use this object to restore its LiveData data. Most importantly, this class also provides another subclass of LiveData, SavingStateLiveData, which can automatically handle data persistence.

In one sentence: ComponentActivity and Fragment use the SavedStateViewModelFactory object as the `Factory` in ViewModelProvider to create ViewModels. As long as the ViewModel provides a constructor with Application or SavedStateHandle, it can enjoy the convenience of restoring data from a Bundle.

## ViewModel's glue: ViewModelProvider
Why is ViewModelProvider the glue? Because this class does just one thing: it combines ViewModelStore and `ViewModelProvider.Factory` to implement a method called `get`, whose internal implementation has two steps.

1. Call ViewModelStore's `get` method to check whether an object has already been created. If it has, return it and the method ends; otherwise, proceed to step 2.

2. Call `ViewModelProvider.Factory`'s `create` method to create the object and save it into ViewModelStore.

So when we want to use a ViewModel, we usually create a ViewModelProvider object and then call the `get` method to obtain the real ViewModel object. In this way, our object has the ability to correctly handle device configuration changes.

## ViewModel's fragment-to-fragment communication functionality
Based on what we've sorted out earlier, we know that ViewModelStore manages a certain ViewModel group. As long as we ensure the ViewModelStore exists, we can ensure the ViewModel survives. Working backward one step: to ensure the ViewModelStore survives, we need to ensure that ViewModelStoreOwner returns the same ViewModelStore object in different places, and both ComponentActivity and Fragment implement this interface. Combined with the fact that an Activity's lifecycle is usually longer than a Fragment's, it's not hard to draw the conclusion — ***in a certain Fragment, creating a ViewModelProvider object with the Activity object guarantees that we get the same ViewModelStore object as the Activity, and therefore the same ViewModel object. As long as the Activity isn't destroyed, all Fragments under that Activity can get the same ViewModel object, and then complete communication by changing state.***

The two levels of abstraction in the creation process are what I find the most brilliant part, and the use of existing conditions (the lifecycles of Activity and Fragment) is also its unique strength.
